## 1. システムの概要

### 1.1 背景

舞鶴工業高等専門学校の鶴友寮では、食堂の献立が学校公式Webサイト上で月別PDFとして公開されている。利用者が当日の朝食・昼食・夕食や、A定食・B定食の内容をスマートフォン等から確認しやすくするため、月別PDFを参照できるWebアプリを構築する。

### 1.2 目的

- 今日の朝食・昼食・夕食を、日付からすぐに確認できるようにする。
- A定食・B定食の違いと、両方に共通する料理を分けて表示する。
- 週間カレンダーや料理名検索で、必要な日の献立を探せるようにする。
- 公式PDFのアレルゲン情報を確認する導線を提供する。
- 学校公式ページに掲載された月別PDF一覧と日別献立データを定期的に更新する。
- 公式PDFを原本として残し、自動抽出内容を確認できるようにする。

### 1.3 システムの位置付け

本アプリは、学校公式情報を見やすく表示する**非公式の補助ビューア**である。献立・アレルゲンの正式な情報源は学校公式ページおよび公式PDFとする。本アプリの表示を、学校による公式発表や安全性の保証として扱わない。

## 2. 対象利用者・利用環境

### 2.1 対象利用者

- 鶴友寮の学生
- 寮の食事内容を確認する教職員・関係者
- 献立表を確認する保護者等

### 2.2 利用環境

- PC、タブレット、スマートフォンのWebブラウザー
- インターネット接続が必要
- GitHub Pagesで公開する静的Webサイトを基本とする
- 日付判定は日本時間（`Asia/Tokyo`）を使用する

### 2.3 公開方式

GitHub PagesではPython等のサーバー処理を実行しない。公開サイトは `site/` 以下のHTML、CSS、JavaScript、JSONで構成する。公式ページの取得およびPDF解析はGitHub Actions上で実行し、生成したJSONをGitHub Pagesに配置する。

## 3. 機能要件

### FR-01 今日の献立の自動表示

1. ブラウザーでページを開いた際、日本時間の日付を取得する。
2. 対応する日別データがあれば、朝食・昼食・夕食を表示する。
3. 表示対象の日付はカレンダーから選択できる。
4. 「今日に戻る」操作で日本時間の当日に戻る。
5. 日別データがない場合は、未取得であることを表示し、該当月の公式PDFへのリンクを案内する。

### FR-02 A定食・B定食の切り替え

1. A定食とB定食を切り替えるボタンを設ける。
2. 選択された定食の料理と、共通料理を同時に表示する。
3. A定食を選択した場合は `A定食の料理 + 共通料理` を表示する。
4. B定食を選択した場合は `B定食の料理 + 共通料理` を表示する。
5. 朝食・昼食・夕食に同じ分類ルールを適用する。

#### FR-02-1 料理項目の分類ルール

料理項目ごとに先頭文字を判定する。前の料理の分類を、次の料理へ引き継いではならない。

| 料理項目の先頭 | 分類 | 表示 |
|---|---|---|
| `A` または全角 `Ａ` | A定食 | A定食を選択したときに表示 |
| `B` または全角 `Ｂ` | B定食 | B定食を選択したときに表示 |
| 上記以外 | 共通料理 | A定食・B定食の両方に表示 |

- 分類記号として先頭のA/Bを取り除き、残りを料理名として表示する。
- 全角・半角等の互換文字は正規化して判定する。
- `共通料理` は区切りを示す見出しであり、料理名として登録しない。
- 先頭・末尾の括弧書きや語句を、分類記号と誤認したり、勝手に削除・補完したりしない。
- 例として `(クリーム)`、`チーズin`、`のり塩コロッ`、`(北海道)`、`豚の`、`カスタード` 等は、抽出された文字列を保持する。
- `のり塩コロッ` 等、途中で切れて見える文字列は、原本で続きが確認できない限り自動補完・他行との自動連結を行わない。

#### FR-02-2 「ごはん」の位置による特別ルール

- B定食の料理の**直下**に独立した `ごはん` または `ご飯` があり、その前に `共通料理` 見出しが現れていない場合、そのごはんはB定食に追加する。
- `共通料理` 見出しの下にある `ごはん` または `ご飯` は共通料理とする。
- B定食の料理とごはんの間に、味噌汁等の別の料理がある場合、ごはんにB定食の分類を引き継がず、共通料理とする。
- PDF抽出時にB定食の料理とごはんが同一行へ連結されている場合も、末尾の独立したごはんを分割し、B定食へ追加する。
- PDFの表抽出時に料理・ごはん・見出しが異なる物理行に分割されても、セル内の並び順を保持して分類する。

### FR-03 週間献立カレンダー

1. 週単位で日付を表示する。
2. 前週・翌週へ移動できる。
3. 日付を選択すると、その日の朝食・昼食・夕食に表示を切り替える。
4. 日別データの有無をカレンダー上で区別する。
5. 日別データが未登録の日は、公式PDFでの確認を案内する。

### FR-04 料理名検索

1. 読み込み済みの日別献立データを対象に料理名を検索する。
2. 入力文字列を含む料理名を検索結果として表示する。
3. 検索結果には日付、食事区分、定食区分、料理名を表示する。
4. 検索結果を選択すると、該当日と該当定食の表示に移動する。
5. 未取得の月・日付は検索対象外であることを明示する。
6. 共通料理はA/B双方の表示に含まれるため、定食別検索結果にも反映する。

### FR-05 アレルゲン情報の確認

対象とするアレルゲンは、次の7項目とする。

| キー | 表示名 |
|---|---|
| `egg` | 卵 |
| `milk` | 乳 |
| `wheat` | 小麦 |
| `shrimp` | エビ |
| `crab` | カニ |
| `buckwheat` | そば |
| `peanut` | 落花生 |

要件：

1. 利用者が確認したい食品を選択し、登録済みの確認情報を検索できる。
2. アレルゲン情報は日付・食事区分・A/B定食別に管理する。
3. PDFの赤丸等の画像情報を、通常のテキスト抽出だけで確定してはならない。
4. 原本未確認の情報は `未確認` と表示する。
5. 学校公式PDFを人が確認して転記したデータのみ `確認済み` とする。
6. 確認済みデータがない場合、アレルゲンなし・該当なしと誤認させない。
7. 原本PDFを開くリンクを表示する。
8. 「該当表示なし」は原本確認済みデータに限って表示し、安全を保証する表現として用いない。

**安全上の注意：** 学校公式資料には、調理時の意図しない混入（コンタミネーション）への注意、原材料を完全除去している人は食べないこと、醤油等の調味料由来の小麦は表示対象外であることが記載されている。アレルギーに関する判断では、必ず最新の学校公式資料・学校からの案内を優先する。

### FR-06 月別献立表の表示

1. 公式ページから取得した月別献立PDFの一覧を表示する。
2. 月を選択できる。
3. 選択したPDFをページ内に表示する。
4. PDFを別タブで開ける。
5. 公式投稿ページおよびPDFのURLを保持する。

### FR-07 データ再読み込み

1. サイト上の「データを再読み込み」は、GitHub Pagesに公開済みのJSONを再取得する。
2. この操作自体は学校公式ページへの再取得やGitHub Actionsの起動を行わない。
3. 公式データの取得・解析はGitHub Actionsによって行う。

### FR-08 更新状況・データ状態の表示

- 月別データ・日別データの読み込み状態を表示する。
- データの更新日時を日本時間で表示する。
- 日別データが部分的な場合は、部分データであることを表示する。
- 抽出できない日付や食事を推測で補完しない。

## 4. データ取得・解析要件

### 4.1 公式情報源

- 献立一覧ページ：<https://www.maizuru-ct.ac.jp/kakuyu/category/dining/>
- 2026年11月のPDF：<https://www.maizuru-ct.ac.jp/kakuyu/wp-content/uploads/sites/3/2026/10/menu-domitory-2026_11-2.pdf>

### 4.2 月別PDF一覧の取得

- `scripts/update_menus.py` が公式の献立掲載ページと各記事を取得する。
- 公式サイトのHTTPS上のPDFリンクのみを対象にする。
- PDFファイル名から対象年月を判定できる場合は、投稿記事の年月よりPDFファイル名の年月を優先する。
- 現行実装はカテゴリーページの先頭およびページ送りを最大3ページ確認し、献立記事とPDFのリンクを抽出する。

### 4.3 日別献立の抽出

- `scripts/extract_daily_menus.py` がPDFを取得し、PyMuPDFを用いて表構造・テキスト位置を解析する。
- 日付、朝食・昼食・夕食、A/B/共通料理、取得可能な栄養価を抽出対象とする。
- 表抽出ができない場合に備え、PDFテキストの座標を使った補助的な解析を行う。
- 抽出内容は `site/data/daily-menus.json` に出力する。
- 実際のPDF構造や改訂状況によって抽出漏れ・誤りが起きる可能性があるため、公式PDFを原本として扱う。

### 4.4 失敗時の扱い

- PDFの取得・解析に失敗した場合、空の日別データを正常な解析結果として公開しない。
- 既に有効な日別データがある場合は、一時的な取得障害時に既存データを保持する。
- 有効な既存データがない場合は、GitHub Actionsの処理を失敗させる。
- PDFの形式変更等で解析できない場合は、Actionsのログを確認し、原本PDFを参照する。

## 5. 自動更新・公開要件

### 5.1 更新時刻

- 毎日、日本時間の **10:35ごろ** にメニューの取得・更新を行う。
- GitHub ActionsのscheduleはUTCで記述するため、設定値は `35 1 * * *` とする。
- GitHub Actionsの実行開始は混雑等により指定時刻から遅れる場合があるため、「10:35ごろ」とする。

### 5.2 起動条件

- 毎日の定期実行：UTC 01:35（JST 10:35）
- `main` ブランチへのpush
- GitHub Actions画面からの手動実行（workflow_dispatch）

### 5.3 更新処理の順序

1. リポジトリをcheckoutする。
2. Python環境を用意する。
3. `requests`、`beautifulsoup4`、`pymupdf` をインストールする。
4. `scripts/update_menus.py` で月別PDF一覧を取得する。
5. `scripts/extract_daily_menus.py` で日別献立を抽出する。
6. `site/` をGitHub Pagesの成果物としてアップロードする。
7. GitHub Pagesへデプロイする。

### 5.4 GitHub Pagesの設定

- GitHubリポジトリの `Settings` → `Pages` → `Build and deployment` → `Source` を `GitHub Actions` にする。
- ワークフロー名は `Update menu data and deploy GitHub Pages`。
- リポジトリ名が `kakuyu-menu` の場合、公開URLは通常 `https://<GitHubユーザー名>.github.io/kakuyu-menu/` となる。

## 6. データ仕様

### 6.1 主なファイル

| ファイル | 用途 |
|---|---|
| `site/data/menus.json` | 月別PDF一覧、掲載日、記事URL、PDF URL、更新日時 |
| `site/data/daily-menus.json` | 日付ごとの朝食・昼食・夕食、A/B/共通料理、栄養価、アレルゲン状態 |
| `site/data/allergen-overrides.json` | 原本を人が確認したアレルゲン情報の上書きデータ |

### 6.2 日別データの構造

日別データは概ね次の構造を持つ。

```json
{
  "date": "2026-11-18",
  "month": "2026-11",
  "meals": {
    "breakfast": {
      "a": ["ごはん"],
      "b": ["ロールパン"],
      "common": ["納豆", "茄子のそぼろあん"],
      "nutrition": {"a": {}, "b": {}, "common": {}},
      "allergens": {"a": null, "b": null},
      "allergen_status": "unverified"
    }
  }
}
```

- 食事区分キーは `breakfast`、`lunch`、`dinner`。
- 料理分類キーは `a`、`b`、`common`。
- アレルゲン未確認時は `allergens.a` / `allergens.b` を `null` とし、`allergen_status` を `unverified` とする。
- 原本照合済みの場合のみ、配列を設定し `allergen_status` を `verified` とする。

### 6.3 アレルゲン上書きデータ

`site/data/allergen-overrides.json` に日付・食事区分・定食別の値を記録する。空配列は「原本を確認し、該当する赤丸がなかった」と確認できた場合だけ使用する。未確認の意味で空配列を使ってはならない。

例：

```json
{
  "2026-11-18": {
    "breakfast": {
      "a": ["egg", "milk"],
      "b": []
    }
  }
}
```

上記は形式例であり、実際の2026年11月18日のアレルゲン値を示すものではない。

## 7. 画面要件

### 7.1 画面構成

1. ヘッダー（アプリ名、学校公式ページへのリンク）
2. 今日の献立（A/B定食切替、朝食・昼食・夕食）
3. 週間献立カレンダー
4. 料理名検索
5. アレルゲン情報の確認
6. 月別献立PDF一覧・PDFビューア
7. 利用上の注意・公式情報源

### 7.2 表示・操作

- スマートフォンの縦画面でも操作しやすいレイアウトとする。
- A/B切替状態が視覚的に分かるようにする。
- 献立データが存在しないことと、料理が存在しないことを混同させない。
- 日別データ未取得の場合は、公式PDFへ誘導する。
- 取得データや検索結果の文字列はHTMLとして解釈せず、安全にテキスト表示する。

## 8. 非機能要件

### 8.1 利用性

- 一般的なスマートフォン・PCブラウザーで利用できる。
- 主要操作は画面上のボタン・入力欄で完結する。
- 献立情報を日本語で表示する。

### 8.2 性能

- 静的HTML/CSS/JavaScript/JSONを基本とし、アプリ利用時に独自サーバーを必要としない。
- PDFは公式サイトから参照し、必要に応じてiframeまたは別タブで開く。

### 8.3 可用性・信頼性

- GitHub Pagesで静的ファイルを公開する。
- 公式サイトやGitHub Actionsが一時的に利用できない場合、公開済みJSONを利用できるようにする。
- 取得失敗を空データや「該当なし」として偽装しない。
- 日別データには出典・取得方式を持たせ、ユーザー転記データとPDF抽出データを区別する。

### 8.4 セキュリティ・プライバシー

- ログイン・個人情報登録・利用者データ収集を要件としない。
- PDF取得先は学校公式ドメインのHTTPS URLに限定する。
- 外部リンクは別タブで開く場合に `noopener noreferrer` を指定する。
- GitHub Actionsには公開に必要な最小限の権限を設定する。

### 8.5 保守性

- データ取得、PDF解析、Web表示、GitHub Pages公開を分離する。
- 分類ルールや例外は自動テストで確認する。
- PDFの形式が変更された場合、解析スクリプトとテストを更新する。

| AC-09 | 月別PDFを選択・表示・別タブで開ける |
| AC-10 | GitHub ActionsがUTC 01:35（JST 10:35ごろ）に実行される設定である |
| AC-11 | データ取得・解析に失敗した際、既存データを不必要に空で上書きしない |
